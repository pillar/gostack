# ADR-0003 Scale 存储：PostgreSQL、SERIALIZABLE 有界重试、占位符改写

- 状态：已采用，2026-11-25
- 范围：PRD §3 Scale 列（PostgreSQL 单主、可多实例、PostgreSQL 任务队列、PG 备份/PITR）、§12 SQLite→PG 迁移、§14 A11。

## 背景

全部业务代码按 SQLite 单写连接编写：`WriteTx` 内大量"先读后写"（`ApplyLedger` 读余额再写账本、领奖读次数再插入、结算读已付再发放、撮合读等待票再建房间）。在 SQLite 上这些事务天然串行；搬到 PostgreSQL 默认的 READ COMMITTED 下会出现丢失更新与重复发放。逐条审计并改写为 `SELECT … FOR UPDATE`/条件更新工作量大且易漏。

## 决定

1. **存储句柄与方言无关**：`adapters/store.DB{Write, Read, Dialect, …}` 提供 `WriteTx`（有界准入 → `ErrOverloaded`，fn 可重跑）、`ReadTx`、`Stats`、`IsUniqueViolation`（同时识别 SQLite 与 SQLSTATE 23505）、迁移执行器。`adapters/sqlite` 与 `adapters/postgres` 只负责打开连接并返回 `*store.DB`。SQLite 行为不变（BEGIN IMMEDIATE、BUSY 重试 3 次、实例锁）。
2. **PG 写事务一律 SERIALIZABLE + 有界重试**：遇 `40001 serialization_failure` / `40P01 deadlock_detected` 在新事务中重跑 fn（默认最多 12 次，2ms→250ms 全抖动退避）。PostgreSQL 的 SSI 保证提交结果等价于某个串行顺序，因此为 SQLite 串行写者写的代码无需逐条审计即可保持正确。即使 fn 吞掉或替换了该错误，驱动连接也会记住 SQLSTATE，`WriteTx` 仍会重试。重试耗尽返回 `ErrContention`（包裹 `ErrOverloaded`，HTTP 503）。读：单语句用读池（READ COMMITTED，连接级 `default_transaction_read_only=on`），`ReadTx` 用 REPEATABLE READ READ ONLY 快照。写入准入（`database.write_queue`）仍是每进程的。
3. **SQL 可移植**：业务 SQL 保留 `?`；PG 连接包装 pgx stdlib 驱动，在字符串字面量、带引号标识符、`$$`/`$tag$` 字符串、`--`/`/* */` 注释之外把 `?`→`$n`、`?NNN`→`$NNN`（SQLite 编号参数），`??` 表示字面 `?`。Go `bool` 参数存为 0/1（两种方言的 schema 都没有 BOOLEAN 列）。不可移植的语句已改写：`INSERT OR IGNORE/REPLACE` → `ON CONFLICT … DO NOTHING/DO UPDATE`；upsert 中的裸列引用加表名限定；标量 `min(a,b)` → `CASE`；`GROUP BY` 补全主键列；`ORDER BY rowid` → 新增 `billing_ledger_entries.seq`（迁移 0011，等于该笔分录后的账户 version）。
4. **迁移**：`migrations/postgres/NNNN_*.sql` 与 `migrations/sqlite/` 一一对应（同版本号、同名），analytics 对应 `migrations/postgres_analytics/`。全部整数列 BIGINT、BLOB→BYTEA、`INTEGER PRIMARY KEY`→`BIGINT GENERATED BY DEFAULT AS IDENTITY`；账本只追加由 plpgsql 触发器实现，并额外阻止 TRUNCATE。`schema_migrations`、校验和漂移与未知版本检测两种方言共用；PG 迁移持有 advisory lock，多实例同时启动只会有一个执行。`TestSchemaEquivalence` 比较两套 schema 的表、列（类型类别与可空）、主键、唯一约束、命名索引、外键与触发器。
5. **排序规则**：PG 数据库必须按字节排序（`LC_COLLATE 'C'`，与 SQLite BINARY 一致）；打开时实测比较结果，不满足则拒绝启动（`ErrCollation`）。
6. **Analytics**：表在 schema `gostack_analytics`，通过 `database.analytics_dsn_ref` 连接（为空时用主库 DSN：同一服务器、独立 schema、独立小连接池与独立 `schema_migrations`）。若需与主库 IO 隔离，请指向另一个数据库或服务器。
7. **队列**：`queue.driver: postgres` 就是同一张 `jobs` 表；Claim 在 SERIALIZABLE 事务中执行并使用 `FOR UPDATE SKIP LOCKED` 降低冲突。**未使用 pgmq**。
8. **配置校验**：`profile: scale` 要求 `database.driver: postgres`、`queue.driver: postgres`、`database.dsn_ref`（env:/file:）；拒绝 lite+postgres、scale+sqlite、`distributed`、scale 下的 `realtime` 模块（进程内 hub，多实例会把玩家分散到不同实例）、scale 下的 `storage.driver: local`、scale 下的 Litestream 备份；lite 下拒绝 PG 专用键。所有限流器仍是**每实例本地**的，scale 必须显式设置 `rate_limit.accept_per_instance: true` 承认"有效配额 = 配置 × 实例数"，避免本地限流冒充全局限流（PRD §3）。
9. **SQLite→PG 迁移工具**（PRD §12）：`gostack migrate to-postgres --from app.db --to-dsn-ref env:X [--analytics-from analytics.db]`。取得 SQLite 实例锁（服务运行时拒绝）、源库 integrity_check 与迁移版本必须与二进制一致、对目标执行迁移并要求所有表为空；在**一个** PG 事务内按外键顺序复制所有表、重置 identity 序列，并在提交前比较逐表行数与确定性摘要（按主键、C 排序、全部列的类型化编码），再运行 GameKit 账本对账与计费对账；任何不一致即回滚（目标保持为空）并以非零码退出，输出 JSON 报告。不做在线双写；切流前需停写并排空队列。
10. **备份**：`backup snapshot/verify/restore` 只适用于 SQLite 文件，配置为 PG 时报错并提示使用 `pg_dump` 或基础备份 + WAL 归档（PITR）。PG 备份由运维负责，本项目未实现也未演练。

## 未实现 / 不在本阶段

- pgmq、Valkey（缓存与全局限流）、PostgreSQL HA / 故障切换 / fencing、Distributed profile。
- 在线双写迁移、PG→SQLite 反向迁移。
- PG 的备份/PITR 自动化与恢复演练。
- 实时（WebSocket）模块的多实例广播。

## 后果与已知限制

- SERIALIZABLE 在热点行（同一账户余额、同一领奖计数、任务 Claim 的过期扫描）上会产生序列化失败与重试，吞吐低于针对性加锁的实现；测试中可观察到大量 40001 被自动重试。性能未在目标环境压测，PRD §13/§23 预算对 Scale **未验证**。
- 文本列不接受 NUL 字节与非法 UTF-8（SQLite 接受）；此类输入在 PG 上会失败（500；PostgreSQL 的已知行为，未专门测试）。迁移工具遇到这类历史数据会整体回滚并报错。
- CHECK 约束未被 schema 等价测试比较（由同一份迁移文本转换并由契约测试覆盖）。
